# 声明服务与动作

`services` 用于让 server connector 发现 kit 提供的 provider。action service 用于让配置页面把操作分发到 kit 内代码。

## 声明服务 provider

在 `kit.json` 中写入服务节点：

```json
{
  "services": {
    "filesystem": {
      "provider": "vendor/name",
      "key": "vendor-name",
      "name": "文件存储",
      "transport": ["direct-upload"],
      "visibility": "private",
      "upload_modes": ["put-presigned"]
    }
  }
}
```

已有 server connector 会按自己的服务 key 读取：

- `filesystem`: 需要 `provider`，通常也需要 `key`。
- `print`: 需要 `provider`，可声明 `transport`、`formats`、`device_types`。
- `trigger`: 当前 workflow 读取 `triggers` 列表。

新增服务类型时，必须同时新增消费方；本包不会自动解释未知服务类型。

## 注册框架服务

如果 provider 需要注册框架服务，可以在 kit 的 `autoload.php` 中调用 `Service::register()` 和 `Service::activeName()`。

当前样例：`server/kits/superpms/localfilesystem/autoload.php` 注册了 runtime-config、prepare-upload、receive-upload 等服务。

## 接入 action service

在 kit 内创建继承 `ServiceApp` 的 action service，并声明：

```php
public static string $lifecycle = ADAPTER_KITS_ACTION;
public static false|string|array $adapter = 'vendor/name';
public static string $hookClass = KitsAdapter::class;
```

入口签名通常是：

```php
public static function entry(
    string $customerUUID,
    string $page,
    string $action,
    mixed $actionDatum = [],
    $id = null,
    ...$args
): mixed
```

平台端和租户端 action 接口会把 `SELECT`、`READ`、`FIND`、`SAVE`、`UPDATE`、`DELETE`、`CREATE` 等动作规范化后传入。

## 页面和 action 的关系

只有 `cfg_pages` 中存在且 `origin === 'action'` 的页面会被分发。页面名会作为 `$page` 传给 action service。

## 可用性检查

服务 connector 通常会同时检查：

- kit 已进入根清单。
- `kit.extra.json.installed` 为 true。
- `kit.extra.json.scope` 允许当前租户类型。
- 如果是租户侧能力，结合 `customer.autoinstall` 或 `SystemKits` 判断当前租户是否可用。
